## Architecture Decisions

### Adopt a lightweight, test-focused augmentation layer for the static site by introducing a TypeScript-based unit test framework (Jest) with DOM testing utilities.

**Rationale:**  ml ong erich.github.io is a GitHub Pages site (static content). Introducing a formal unit test layer ensures core utilities, data processing helpers, and UI helpers are robust, modular, and regressions are caught early. TypeScript provides type safety and clearer interfaces for future contributors. Jest offers a wide ecosystem, good TypeScript support (ts-jest), and simple CI integration.

**Impact:** Adds devDependencies (TypeScript, ts-jest, Jest, DOM testing libs). Requires a small project config (tsconfig, jest.config.js) and CI steps to run tests on PRs.

**Risks:** If the codebase is largely HTML + static JS without modules, testing DOM logic may require refactoring to isolate testable units. TypeScript adoption may require incremental typing of existing JS files.

## Implementation Plan

### Overview
Establish a scalable unit testing foundation first, then progressively expand coverage to core utilities, data processing helpers, and UI helpers. Integrate tests into CI with a coverage gate and document the testing approach.

### Critical Path
Core utilities identification → Jest/ts-jest config → first 2–3 unit tests → CI integration and coverage gate. UI tests are optional but recommended if UI logic exists.

## Technology Recommendations

### Testing framework
**Recommendation:** Jest with ts-jest (if using TypeScript) or plain Jest (if staying with JavaScript).
**Rationale:** Stable, widely adopted, good TypeScript support, ecosystem of matchers, and straightforward CI integration.

### DOM/UI testing
**Recommendation:** @testing-library/dom or @testing-library/react (if React is used).
**Rationale:** Encourages testing from the user's perspective, stable tests, and easy maintenance.

### Linting & formatting
**Recommendation:** ESLint + Prettier, with TypeScript plugin if TS is used.
**Rationale:** Ensures code quality and consistency across contributors.

### CI & deployment
**Recommendation:** GitHub Actions with Node.js matrix, cache node_modules, and run tests on PRs.
**Rationale:** Seamless integration with GitHub Pages workflow and PR gating.

### End-to-end testing (optional)
**Recommendation:** Playwright or Cypress for UI flows (if needed).
**Rationale:** Reliable UI end-to-end validation beyond unit tests.

## Technical Risks

### Limited modularity in codebase hindering testability (tight coupling and global state).
**Probability:** Medium
**Impact:** Medium
**Mitigation:** Refactor toward pure, modular functions; externalize DOM-specific logic into testable modules; introduce dependency injection where feasible.

### Flaky tests due to DOM timing or network mocks.
**Probability:** Medium
**Impact:** Medium
**Mitigation:** Use explicit DOM polling, deterministic mocks, and isolated test environments; prefer unit tests over flaky integration tests; cap test timeouts.

### Increased CI time or resource usage.
**Probability:** Medium
**Impact:** Medium
**Mitigation:** Parallelize tests, enable caching for node_modules, limit test scope per PR, and run a lightweight baseline suite on every PR with a longer full suite nightly.

### Adoption friction for TypeScript in a predominantly JS repo.
**Probability:** Medium
**Impact:** Medium
**Mitigation:** Adopt a gradual approach: start with JS tests or incremental TS typings; provide a simple tsconfig and minimal type definitions to ease onboarding.

## Performance Considerations

**Scalability:** Unit tests are inherently scalable; ensure test suite remains fast. Avoid heavy E2E tests in PRs to keep feedback quick.

**Performance Targets:** Aim for 60–120 seconds total CI runtime for the full suite; sub-60 seconds for PR baseline with a longer nightly run.

**Optimization Strategies:** Limit tests to pure units first; mock network and DOM where possible.,Use jest --runInBand only if necessary; otherwise enable parallel workers.,Cache dependencies in CI to reduce install time.

## Security Considerations

**Threat Model:** Minimal risk for a static site; focus on supply-chain risk via dependencies.

**Security Controls:** Regular npm audit during CI or pre-commit checks.,Lockfile integrity (package-lock.json/yarn.lock) to ensure reproducible builds.

**Compliance:** Ensure no secret keys or credentials are committed; tests should not access external services without secure mocks.

## Development Strategy

**Methodology:** Agile-oriented discovery with incremental Sprints; prioritize core utilities first.

**Testing Strategy:** Start with unit tests for pure functions and utilities,Add DOM tests for UI helper logic,Introduce optional UI E2E tests if UI flows exist

**Deployment Strategy:** GitHub Pages will rebuild on pushes to main; ensure tests pass prior to merge,No production deployment of a backend; changes are static site updates
