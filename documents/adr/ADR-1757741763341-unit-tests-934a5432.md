## Context

This analysis proposes a language-agnostic unit test duplicate detector tool (initial MVP focused on identical test bodies in JavaScript/TypeScript) with AST-based parsing, delivered as a CLI and GitHub Action. The detector can gate PRs or generate reports, expanding to additional languages and more sophisticated similarity metrics over time. The plan emphasizes CI integration, clear reporting, and a phased approach with risk mitigations around false positives, performance, and parser coverage. Collaboration with the BA is needed to finalize the MVP scope, success metrics, and gating behavior before implementation begins.

## Architecture Decisions

### Adopt a language-agnostic unit test duplicate detector tool with modular, AST-based parsing and integrate it into CI as a gate or report artifact.

**Rationale:** A language-agnostic approach allows the detector to scale across multiple languages and test frameworks. Using AST-based comparison focuses on test bodies and structure rather than textual similarity, reducing false positives from cosmetic edits. A modular design enables easy extension to additional languages and test frameworks in the future. Integration with CI provides a controllable gate or reporting artifact aligned with business goals.

**Impact:** Produces a reusable tooling artifact that can be adopted across projects. Enables early detection of duplicates, improves maintainability, and supports governance as part of PR workflows.

**Risks:** False positives/negatives due to heuristic limits; performance impact on large repos; maintenance burden for parsers across languages; security considerations in CI runners.

## Implementation Plan

### Overview
Develop a lightweight detector CLI (Node.js) with language-agnostic parsing (via tree-sitter or language-specific ASTs) to identify duplicate test bodies. Ship as an npm package and provide a GitHub Action to run on PRs or on schedule, with an optional report artifact and PR annotation.

### Critical Path
Defining MVP duplicate criteria and implementing Phase 2 core detector are the critical path pieces. Without a working detector, CI gating cannot be evaluated. Phase 3 CI integration relies on Phase 2 stability and adapter readiness.

## Technology Recommendations

### Detector runtime
**Recommendation:** Node.js (TypeScript) with a pluggable architecture; core logic in a CLI tool; adapters for JS/TS first, Python/Java later.
**Rationale:** Widely used in GitHub Actions; rich ecosystem for parsing JS/TS; easy to expose as npm package and as a GitHub Action.

### Parsing & AST
**Recommendation:** Tree-sitter-based parsers for multi-language support; language-specific adapters for JS/TS (ESTree/Babel) and Python (ast).
**Rationale:** Accurate structural parsing, language-agnostic comparison at the AST level; robust handling of modern language features.

### CI integration
**Recommendation:** GitHub Action with optional gating and PR annotation; provide an npm package for local usage.
**Rationale:** Seamless integration with mlongerich/mlongerich.github.io workflow; easy adoption for maintainers.

## Technical Risks

### False positives/negatives in duplicate detection due to semantic differences in test bodies.
**Probability:** Medium
**Impact:** Medium
**Mitigation:** Start with strict identical bodies as baseline; add normalization (e.g., ignoring comments, whitespace); progressively add semantic similarity heuristics and optional coverage overlap metrics.

### Performance and memory pressure on large repos with numerous tests.
**Probability:** Medium
**Impact:** Medium
**Mitigation:** Stream parsing, incremental scans, and caching of parsed ASTs; parallelize across files with worker threads; limit scope by default (e.g., top-level test directories).

### Language parser drift or unsupported constructs causing parsing failures.
**Probability:** Medium
**Impact:** Medium
**Mitigation:** Maintain adapters with a clear support matrix; add fallback to textual normalization when parsing fails; monitor and log parsing errors.

### Security and CI runner isolation concerns.
**Probability:** Low
**Impact:** Medium
**Mitigation:** Run detectors in isolated CI environments; avoid executing user code; pull sources via checkout; no network calls from detector.

## Performance Considerations

**Scalability:** Design for linear scans with per-file AST parsing; support parallel processing to scale with repo size.

**Performance Targets:** Detect duplicates within a 5–10 minute window for mid-sized repos; maintainable performance for large repos with configurable scopes.

**Optimization Strategies:** Stream file enumeration and incremental AST parsing,Caching parsed ASTs per file with invalidation on file changes,Language-specific quick-paths for trivial duplicates (e.g., identical test names) as early filters

## Security Considerations

**Threat Model:** Detector runs in CI; potential exposure if misused to access repository data; no network access by design.

**Security Controls:** Isolated CI runner usage; run with minimal permissions,Do not execute arbitrary code from tests; only parse/read files,Validate and sanitize inputs to detector (config-driven)

**Compliance:** Ensure no leakage of sensitive data via reports (redact paths or use hashed identifiers in reports if needed)
